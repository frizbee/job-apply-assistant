# Indeed: страница входа не должна прерываться новыми поисковыми переходами

## Актуальное исправление: один возврат к поиску после входа

Поисковый переход теперь обрабатывает `IndeedAdapter.indeed_open_search`.
Он запоминает **точный исходный URL** (заголовок, географию, период и сортировку
не меняет), наблюдает HTTP-статус основного документа до начала навигации и
ожидает вход в той же вкладке. OAuth-пути и session-manager распознаются как
промежуточная авторизация. Cookie/token/OAuth-query данные не извлекаются.

Если после входа Indeed вернул на главную, один возврат к поиску разрешается
только при всех условиях:

- основной документ этой главной получил HTTP 200;
- HTTPS-адрес принадлежит Indeed, путь — главная, не auth/чужой сайт;
- нет CAPTCHA/блокировки, формы входа или видимой кнопки Sign in;
- есть видимое меню аккаунта либо явный Sign out (положительное свидетельство
  авторизованного интерфейса, а не просто отсутствие CAPTCHA);
- страница стабильна не менее секунды; новый документ перезапускает таймер;
- пользователь не нажал Stop, время прогона не истекло.

Перед goto попытка резервируется: в рамках этого поиска она только одна, даже
при ошибке навигации. Новая вкладка не создаётся, reload не вызывается. Если
после возврата снова появляется 401/403/429, CAPTCHA или видимая форма входа,
текущий источник останавливается без повторной просьбы пройти авторизацию.
Если сайт снова вернул главную, второй goto не выполняется; действует обычный
ограниченный таймаут ожидания. Для detail/application-потоков это восстановление
не включается, кнопки отправки и история остаются под прежними защитами.

При неизвестной разметке аккаунта автоматический возврат намеренно не делается:
пользователь может вручную вернуться к поиску в том же окне. Откат к старому
условию «не CAPTCHA значит выдача готова» не выполнялся.

**644 теста успешно**, включая 12 локальных Chrome-проверок восстановления:
успешный и пустой поиск, сохранение URL/одной вкладки, возврат на home/login/
challenge, неподтверждённые/пустые/403 главные, Stop/deadline, неверные адреса,
очистку наблюдателя и стабильность документа. Живой доступ к Indeed после этого
исправления ещё не подтверждён: серверный 403 этим изменением не обходится и
не считается исправленным. Новые реальные заявки не отправлялись.

Дополнительно источник теперь останавливается, если основная цепочка
`OAuth callback → документ 401/403/429` отклонила доступ **до** нашего возврата
к поиску. Это прекращает повторные просьбы пройти вход в рамках текущего
ожидания. 403 от fetch/телеметрии не считается отказом основного документа;
отдельная Chrome-фикстура проверяет это различие. Диагностический CLI также
обрабатывает SIGINT/SIGTERM через штатную очистку и поддерживает файл `stop`,
чтобы остановка не требовала принудительного разрыва Playwright-процесса.

Ниже сохранена история предшествующих изменений и диагностик.

## Причина

Ранее `goto(..., "Indeed")` ожидал только исчезновение признаков CAPTCHA через общий `page_ready()`. Страница входа без такого признака могла считаться готовой. Поиск получал пустой список `[data-jk]` и открывал следующий keyword, прерывая ручной ввод. Короткий пустой документ между редиректами также мог ошибочно пройти проверку «не CAPTCHA».

В application-flow отдельно распознавались только пути `secure.indeed.com/(auth|account)`, без полной поддержки других login/account URL и форм входа на исходном URL.

## Изменения

- Добавлено Indeed-specific ожидание `indeed_wait_ready()` для переходов к поиску/detail и для application-flow.
- Распознаются auth/account/login пути, account/auth-поддомены, видимые password/username-поля и заголовки входа. Внешняя OAuth-страница не считается готовой Indeed-формой.
- Требуется положительное свидетельство нужной стадии: карточки или явный no-results блок для поиска, detail-контейнер для вакансии, application controls для формы. Отсутствия CAPTCHA недостаточно.
- После появления готовой страницы проверяется стабильный URL/состояние не менее секунды. Промежуточный blank/redirect документ сбрасывает ожидание.
- В первоначальном исправлении ожидание было полностью пассивным, до 10 минут, с поддержкой Stop. Теперь добавлено только ограниченное восстановление поиска, описанное выше; reload по-прежнему не вызывается. Если вход/проверка не завершены, текущий source останавливается, а не открывает следующий keyword. Логин/OTP/пароль приложение не заполняет.
- Другие площадки остаются на прежней ветке общего navigation helper; их адаптеры не менялись. Submit guards, история и пользовательские настройки не ослаблялись/не сбрасывались.

## Проверка

**498 тестов прошли**, включая 8 новых unit/локальных Chrome-проверок: сохранение введённого email при нескольких проверках, один app-goto без reload, отсутствие перехода к следующему keyword во время входа, blank redirect, auth overlay поверх результатов, timeout и отсутствие заполнения application до входа. Изолированная navigation-регрессия использует уже готовую форму; проверка входа покрывается отдельными тестами.

```bash
AUTOAPPLY_BROWSER_TESTS=1 .venv/bin/python -m unittest discover -s tests
```

В реальном Chrome Indeed вернул HTTP 403, title `Just a moment...`, `Additional Verification Required`. В диагностике после исправления: 12 секунд пассивных проверок, **app-goto=1, app-reload=0**, шесть `ready=false`, следующий keyword не открыт. Три события навигации main frame происходили на стороне сайта, не от дополнительных вызовов навигации приложения. Успешный реальный вход/заполнение не подтверждены, отклики не отправлялись. SHA-256 основных history/settings/CSV/log файлов не изменились.

Локальные диагностические результаты: `data/browser-diagnostics/indeed-auth-review/before-fix.json`, `after-fix.json` (Git ignored).

## Оставшееся ограничение

Код не может гарантировать отсутствие собственных обновлений Indeed/Cloudflare и не обходит проверки. Если после перезапуска приложения страница продолжает обновляться, нужно отличать сайт-инициированные переходы от app-goto; автоматическое повторение поиска или смена fingerprint/proxy ради обхода проверки не добавлялись. Для применения исправления необходимо перезапустить GUI и начать новый тест.

## Повторяемая живая проверка доступа

```bash
.venv/bin/python tools/indeed_readiness_smoke.py --wait-seconds 90
```

Диагностика использует production-адаптер Indeed, первый сохранённый заголовок
поиска и существующий запрос `l=Remote`. Это **не проверка соответствия выбранным
странам/регионам**: их отображение на нативную географию Indeed ещё нужно проверять
отдельно. До этого диагностика не открывает заявки, не заполняет поля и не
загружает CV. История и настройки не меняются; отчёт и скриншот сохраняются
в приватном `data/browser-diagnostics/indeed-access-…/`.

Видимый Chrome позволяет пользователю вручную завершить вход/проверку. Ожидание
по умолчанию ограничено 90 секундами (допустимый аргумент 5–600;
`--wait-seconds 600` даёт 10 минут на ручной вход). Отдельно записываются HTTP
статусы навигаций, положительные признаки выдачи и счётчики вызовов app-goto /
app-reload. Статус blocked не считается пустой выдачей или успешным тестом формы.
Инструмент чтения выдачи больше не устанавливает request interception: никакие
application callbacks из генератора вакансий не вызываются, поэтому сетевой
перехват для защиты от отправки здесь не нужен. HTML страницы не сохраняется.

Для продолжительного ручного входа в **том же** управляемом окне:

```bash
.venv/bin/python tools/indeed_readiness_smoke.py --wait-seconds 600 --manual-login
```

Окно остаётся открытым до 10 минут, даже если поиск сначала доступен. После
ручного входа нужно вернуться к исходному поиску в этом окне. Скрипт не повторяет
goto после входа, не переключает keyword и не перезагружает страницу; по
окончании проверяет текущую выдачу и читает не более пяти карточек. Режим не
проверяет application-flow или повторную навигацию production-адаптера. Для
досрочного продолжения после явного подтверждения пользователя можно создать
пустой файл `continue` внутри напечатанного диагностического каталога.

Для пассивной диагностики самой проверки, **без перехвата запросов**:

```bash
.venv/bin/python tools/indeed_challenge_diagnostic.py --wait-seconds 120
```

Параметры запуска/profile не подменяются. Собираются HTTP-статусы, только
разрешённые диагностические заголовки (server/cf-ray/cf-mitigated/content-type),
категории сетевых/CSP-ошибок, числовые коды Turnstile и признаки состояния iframe.
Cookies, storage state, тела ответов, сырые сообщения консоли и полные challenge
URL не сохраняются. Поиск и application-flow не изменяются, скрипт ничего
не нажимает и не заполняет. Это диагностика, не обход защиты и не доказательство
внутренней причины решения Cloudflare.

Cloudflare явно относит Playwright и другие автоматизированные браузеры к
[неподдерживаемым средам для production challenges](https://developers.cloudflare.com/cloudflare-challenges/reference/supported-browsers/).
Поэтому ручной клик CAPTCHA внутри управляемого Chrome сам по себе не гарантирует
прохождение. Значения полученных кодов нужно сверять с
[официальным справочником Turnstile](https://developers.cloudflare.com/turnstile/troubleshooting/client-side-errors/error-codes/):
например, отдельный 401 может быть штатной попыткой Private Access Token, а не
причиной блокировки. Нельзя объявлять любой сетевой сбой или факт использования
Playwright доказательством конкретного триггера без данных.

### Пассивная проверка 2026-10-24

Отчёт: `data/browser-diagnostics/indeed-challenge-20261024T195238446632Z/report.json`.
При неизменных настройках запуска, без request interception, за 120 секунд
получены 7 ответов поиска HTTP 403 с `cf-mitigated: challenge`. Скрипты, iframe
и XHR Cloudflare загружались с HTTP 200; браузер сообщает cookies enabled,
JavaScript выполняется. App-goto=1, app-reload=0, ready=false. Отправок нет,
рабочие файлы не изменились, cookies/токены не извлекались.

Замечены CSP-сообщения, блокировки telemetry-ping `t.indeed.com` и aborted fetch
`hagen.challenges.cloudflare.com`; эти категории **не доказывают причину**
непрохождения challenge. Точные CSP-директивы этим запуском не сохранялись.
Отдельные 401 при challenge сами по себе также не доказывают сбой проверки.
Подтверждён повторный challenge после загрузки/исполнения его ресурсов, но
внутренний фактор отказа (automation/profile/другая проверка) неизвестен. Обычный
пользовательский Chrome этим инструментом не исследовался; контролируемого
сравнения двух сессий нет. Не следует объявлять конкретный fingerprint, IP или
cookie причиной без дополнительного подтверждения.

### Повторная проверка после ручного входа в профиль приложения

Пользователь вошёл в Indeed в обычном Chrome с тем же `.browser-profile` и
затем полностью завершил Chrome. Первый автоматизированный запуск получил
HTTP 200 на `/jobs`, ready=true, blocked=false:
`data/browser-diagnostics/indeed-challenge-20261024T202033838014Z/report.json`.

Следующий запуск сбора карточек получил 403 и перешёл на Indeed Sign In.
После удаления перехвата запросов из диагностического инструмента результат
повторился: 403 → `/account/login` → `/auth`, auth_pending=true, карточек 0.
Отчёт: `data/browser-diagnostics/indeed-access-20261024T202148005749Z/report.json`.
Во всех проверках отправок и открытия форм 0, рабочие файлы не изменены.

Таким образом, один успешный доступ подтверждён, но устойчивость сессии/поиска
не подтверждена. Не доказано ни то, что cookies потерялись, ни то, что именно
перехват запросов вызвал отказ. Нельзя считать Indeed готовым к автоматическому
прогону на основании единственного HTTP 200. Следующие повторные входы без
новых диагностических оснований не должны автоматически запускаться циклом.

### Сравнение с исходным репозиторием

Исходник зафиксирован на `klncgty/linkedin-auto-apply@7fd1748c31d395d21c52efc1eb44728344db938f`.
Запуск Chrome, алгоритм выбора `.browser-profile`, параметры browser context,
URL Indeed-поиска и закреплённый Playwright 1.48.0 совпадают с текущей версией.
Поиск/парсер после механического извлечения в платформенный класс сохранились;
отличие callback — передача истории защищённой отправки.

Изменилось ожидание: upstream `page_ready = not core.blocked(page)` может
принять login/home/blank как готовую выдачу. Текущая версия требует положительных
признаков search/detail/application. Если после входа пользователь вернулся
на главную, текущая search-проверка не продолжит поиск сама — это отличие
сценария, которое требует отдельного решения, но само не доказывает причину 403.

Команда сравнения без отправок и без исполнения чужого application-кода:

```bash
.venv/bin/python tools/indeed_upstream_compare.py --seconds 60
```

Перед запуском проверяется AST-эквивалентность upstream/local `page_ready`.
Оба условия наблюдают одну страницу/сессию, запрос открывается один раз.
Это сравнение предикатов готовности, **не полноценный A/B всего старого бота**.
Обновлённый инструмент отбрасывает измерения при смене документа/URL между
чтениями, чтобы редиректы не выглядели расхождением двух условий.

Первый живой прогон сравнения:
`data/browser-diagnostics/indeed-upstream-compare-20261024T204048958575Z/report.json`.
Уже исходный запрос `/jobs` вернул 403; на challenge обе проверки были false.
Наблюдались возвраты OAuth и страницы без карточек, которые старый предикат
мог принять. Часть измерений совпала с редиректами (в одном измерении
`legacy_ready=true` и последующий `blocked=true`), поэтому они не являются
доказательством расхождения на одном неизменном документе. Отправок 0,
app-goto=1, app-reload=0, рабочие файлы не изменены. Локальные Chrome-фикстуры
подтверждают различие на login/home и совпадение на challenge/results:
11 Indeed login/wait тестов прошли. Откат ожидания сам по себе не доказан
как исправление текущего сетевого отказа; историческая работоспособность
оригинального кода этим экспериментом не опровергается.

### Причины отклонения cookies и сети, 2026-10-24 21:06 UTC

Пассивная проверка через CDP Network, без interception, изменения cookies или
параметров браузера:

```bash
.venv/bin/python tools/indeed_cookie_diagnostic.py --seconds 60
```

Отчёт: `data/browser-diagnostics/indeed-cookie-policy-20261024T210646694875Z/report.json`.
Сохраняются только категории cookies и причины включения/отклонения — без
значений, Cookie/Set-Cookie строк, OAuth-query, storage state или сырых CSP
сообщений. Browser policy Preferences читаются лишь по нескольким известным
скалярным ключам; ничего не переписывается.

На начальном `/jobs` и двух возвратах на `/` Chrome включил `cf_clearance`,
Cloudflare cookie и 35 site cookies в каждый запрос. Сервер ответил HTTP 403,
`cf-mitigated: challenge`. OAuth callback наблюдался дважды. В записанных
cookie-metadata были только `NotOnPath` / `DomainMismatch` для исключённых
cookies; отклонений Set-Cookie и причин вроде ThirdPartyPhaseout не записано.
Это не доказывает валидность каждого session-cookie на сервере, но опровергает
простое объяснение «профиль не загружен / все cookies отсутствуют». Наличие
clearance-cookie не гарантирует, что Cloudflare примет его или не назначит
дополнительную проверку. Конкретный внутренний фактор решения неизвестен.

`ERR_BLOCKED_BY_RESPONSE` здесь относится к `t.indeed.com` telemetry-ping и
имеет COEP/CORP-причину `corp-not-same-origin-after-defaulted-to-same-origin-by-coep`.
Его нельзя объявлять причиной отказа авторизации без иных данных. CSP-сообщения
содержали connect-src; скрипты/iframe/XHR challenge загружались с HTTP 200.
Явного запрета cookies/JavaScript в прочитанных ключах профиля не обнаружено
(ключи отсутствуют, то есть это не доказательство всех эффективных политик).
Рабочие файлы не изменились, application actions=0. Новые Chrome-проверки
останавливают OAuth-цикл на реальном документном отказе, но не обходят его.
