# LinkedIn / Rails: исправления и дальнейший fix-list

Дата проверки: 2026-10-22. Реальные отклики не отправлялись. Это отчёт о доступной проверке, не подтверждение готовности всех live-форм.

## Поправка: пользовательские регионы имеют приоритет

По последующему требованию пользователя удалены `argentina_location_reason` и автоматический допуск страны из CV / прежнего `accepted_regions`. География не является частью Rails-политики. Прежние пункты об Argentina-only ниже описывают прошлый прогон, а не актуальное поведение.

- Поиск LinkedIn использует введённые регионы без замены или расширения. Персональные Jobs/recommended feeds исключены, так как они не ограничены пользовательским списком.
- В локальных настройках восстановлены явно названные пользователем **North America, Latin America, Europe**. Больше никакие поля профиля, история или персональные ответы в этой поправке не изменялись.
- Пустой список вызывает ошибку вместо скрытого fallback; конфигурация используется только при отсутствии сохранённого списка. Настройки регионов применяются и без CV-профиля.
- Сведения о стране проживания не добавляют регион и не отклоняют LinkedIn-вакансию. Метка локации офиса не доказывает право работать. Дата, remote-only и защита от повторной отправки продолжают проверяться.
- Queryless-площадки сопоставляют буквально выбранные пользователем региональные метки; автоматического преобразования стран в континенты нет.
- Передача регионов в поисковые URL покрыта регрессиями. Применение фильтров самим LinkedIn после его редиректов по-прежнему требует отдельной live-проверки; исправление не заявляет её успешной.

## Исходный результат и причины

В истории было 56 записей: 42 `metadata_manual` с `posting_date_unknown`, 14 `title_not_relevant`. Два запуска дали 0 previews.

1. **Дата:** реальные доступные авторизованные LinkedIn-страницы используют новый SDUI DOM, хешированные CSS-классы, параграф вместо `h1` и не содержат JSON-LD. Старые селекторы возвращали `labels=[]`, `times=[]`, `postings=[]`. В проверенных страницах язык `en`, дата при этом видна, например `Reposted 2 days ago`. Следовательно, причина подтверждённого сбоя — неподдерживаемый DOM, а не отсутствие даты или необходимость подставить текущую дату. Нельзя утверждать, что лично просмотрены все 42 исходные страницы.
2. **Identity:** заголовок вкладки реально имеет вид `Grupo QuintoAndar | Staff Software Engineer | QuintoAndar | LinkedIn`. Старое позиционное разбиение принимало префикс за должность, а должность — за компанию. В самой карточке компания — `QuintoAndar`, должность содержит отделяемый подтверждённый префикс `Grupo QuintoAndar`.
3. **Релевантность:** единственная прежняя целевая роль `Software Engineer` превращалась в слова `software|engineer`, а обязательная роль — в `engineer`. Поэтому Ruby/Rails Developer не проходили, но нерелевантные специализированные Engineer могли проходить.
4. **История:** ручные/фильтровые решения были терминальными без отдельного безопасного механизма повторной оценки.

## Выполнено

- [x] `job_metadata.py`: старые, public и новые SDUI header-layouts; привязка нового header к `JobDetails_ManageJobBanner_<current ID>`, без чтения даты из рекомендаций или описания.
- [x] Ограниченное ожидание гидратации, включая уже появившийся header с ещё отсутствующей датой. Не более 5 инспекций, по умолчанию 3.
- [x] Консервативные относительные даты EN/ES/PT/TR/RU. Для «2 days ago» используется старейший край интервала — 3 дня назад; «1 week ago» не считается доказательством публикации за последние 7 дней. Поисковые фильтры не являются доказательством свежести. Дата repost в header остаётся свидетельством repost, не доказательством первоначальной публикации.
- [x] JSON-LD принимается только для сопоставленной вакансии; относительные URL тоже проверяются, а не превращаются в анонимное совпадение. При неизвестной дате — manual с языком, числом header/JSON-LD, количеством инспекций, найденными date-evidence и диагностикой.
- [x] `job_info()`: текущая карточка/проверенный JSON-LD вместо предполагаемого порядка вкладки. Два QuintoAndar случая покрыты регрессиями. Без подтверждаемой identity — `relevance_manual: identity_unknown`.
- [x] `job_relevance.py`: opt-in `relevance_profile=rails_backend`. Явные Ruby/Rails Developer/Engineer/Lead допускаются; общие backend/full-stack/software/lead требуют положительного свидетельства Rails в описании. Совпадения `senior`/`engineer` сами по себе недостаточны.
- [x] Отдельный запрет специализированных mobile/data/SRE/Kubernetes/DevOps-ролей, обязательного несовместимого backend-стека. Nice-to-have и preferred не превращаются в обязательное требование; Rails только в optional-секции не доказывает пригодность общей роли. Неопределённая миграция стека — manual.
- [x] Для этого кандидата включена проверка доступности из Аргентины. `Argentina`, LATAM/South America и worldwide допускаются при отсутствии противоречащих ограничений; просто `Remote` без региона требует ручной проверки. EU/US-only не разрешаются старым широким региональным regex.
- [x] В локальных пользовательских настройках заданы девять согласованных целевых ролей, поиск Argentina/Latin America/Worldwide и явно подтверждённые 14 лет Ruby/Rails. Контакты, город/страна кандидата, общий стаж, CV-файл и зарплатные ожидания не изменялись. Внутри `cv_profile` изменено только `job_titles`.
- [x] `job_rechecks.py`: opt-in пересмотр только `metadata_manual`, `title_not_relevant`, `relevance_manual`; по умолчанию максимум 10 за запуск, 3 на вакансию суммарно, cooldown 24 часа для той же ревизии. Новая ревизия парсера/профиля/фильтров допускает пересмотр раньше cooldown, но не отменяет суммарный лимит.
- [x] Перед миграцией создаётся backup; первоначальные и последующие решения сохраняются в `decisions` вместе с причинами, identity, датой/временем и ревизией новой оценки. Метаданные `recheck` хранят счётчик, время, run ID и revision. Старое поле `date` имеет точность только до дня; точное старое время не выдумывается.
- [x] Manual-статусы не добавлены в глобальный `can_retry`. В `evaluation_passed` переводятся только после повторного прохождения фильтров и metadata/location gates. Подтверждённые, pending, uncertain и rejected отправки не переводятся в recheckable. Прямой `process_job()` тоже не переписывает такие записи и не обходит разрешение пересмотра.
- [x] Дубликаты LinkedIn ID внутри одного запуска не вызывают повторную обработку. Неизвестная дата/стек не создаёт бесконечный retry-loop.

## Регрессионные тесты

Добавлены 29 целевых проверок: локализованные/неизвестные даты, новый DOM, поздняя дата, QuintoAndar, верифицированный JSON-LD, Rails/general/specialist/required/optional, Argentina, резервное копирование, audit, bounded rechecks и запрет разблокировки отправок.

**Полный локальный прогон: 448 тестов прошли (329 unit + 119 браузерных).**

```bash
AUTOAPPLY_BROWSER_TESTS=1 .venv/bin/python -m unittest discover -s tests
```

На локальной HTML-фикстуре полный pipeline проходит suitability/metadata gates, открывает форму, заполняет Ruby experience = 14, возвращает dry-run и не вызывает submit. Это **не** выдаётся за успешное заполнение реальной формы работодателя.

Для ручного live smoke-test сначала остановить активный worker GUI:

```bash
.venv/bin/python tools/linkedin_dry_run.py --job-id <numeric-linkedin-id>
```

Только 1–10 ID, один preview на запуск; обычные gates/history/recheck caps продолжают действовать. Не менять файл CV во время теста. После обновления кода необходимо перезапустить GUI, чтобы старый процесс не использовал прежние функции.

## Оставшийся enhancement / fix-list

1. **P1 — поддержка Proxify.** Отдельно исследовать целевые формы `career.proxify.io` / `talent.proxify.io`, их происхождение, поля, consent, загрузку CV и native/JS submit. Нужен специализированный проверяемый адаптер и live dry-run; простое добавление hostname в whitelist запрещено как решение. Критерий: одна подходящая реальная форма заполнена, ноль отправок.
2. **P1 — live Easy Apply на новой SDUI-форме.** Добыть доступную подходящую Rails-вакансию с подтверждённым регионом/датой и проверить открытие, шаги, uploads и final guard. Текущий локальный тест не доказывает совместимость актуальной live-формы.
3. **P2 — структура требований.** Расширить evidence-based разбор многоязычных headings/стека и точных географических ограничений; сохранять причины/фрагменты mandatory vs optional для решения пользователем. Regex-классификация намеренно консервативна, не является полной семантической оценкой.
4. **P2 — диагностика/выдача поиска.** Проверить новый `jobs/search-results` и изменения региона/фильтров LinkedIn; явно показывать фактическую область и нулевые результаты вместо предположения, что URL-фильтры применились.
5. **P2 — управление пересмотром в GUI.** Показать оставшийся бюджет, счётчик, историю решений и явно подтверждаемую очередь переоценки. Сейчас доступен opt-in в настройках и ограниченная автоматическая проверка. Новые терминальные фильтровые статусы/`external_manual` не разблокируются этой миграцией автоматически.
6. **P2 — межпроцессная блокировка history/browser profile.** GUI-lock и атомарный `replace` не заменяют блокировку двух экземпляров приложения; параллельные GUI/CLI workers запрещены операционно.
7. **P2 — readonly выгрузка audit.** Добавить компактный экспорт причин и переходов без персональных полей; не публиковать приватные HTML-снимки/логи.
8. **P2 — выпуск.** Проверить Windows/macOS binaries после новых модулей; релизная упаковка и живые страницы остальных площадок в этом прогоне не проверялись.
