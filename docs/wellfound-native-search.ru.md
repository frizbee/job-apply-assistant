# Wellfound: нативный поиск по полным GUI-должностям

Дата: 2026-10-22. Изменения изолированы в `wellfound_search.py` и Wellfound-секции `sources.py`. Общие фильтры, GUI, конфигурация и функции остальных адаптеров не менялись.

## Почему больше не нужен guessed role slug

В авторизованном `/jobs` есть настоящий фильтр **Included keywords**, отличный от глобального **Search everything**. Проверено в браузере: полное `Senior Ruby on Rails Developer` передаётся в запрос `JobSearchResultsX` как `filterConfigurationInput.keywords = ["Senior Ruby on Rails Developer"]`.

Новый путь не снимает `Senior`, не заменяет Developer на Engineer, не создаёт список технологий/профессий и не переписывает GUI-должности. Семантика поиска keywords определяется самой площадкой: это не обещание строгого совпадения только с названием роли. Общие пользовательские фильтры продолжают применяться после получения результатов.

## Реализация

- Для Wellfound создаётся отдельная поисковая вкладка в имеющемся авторизованном контексте. Приложение работает через штатные поисковые контролы; вручную не воспроизводит API-запросы и не подделывает служебные заголовки. Прямой запрос вне штатного браузерного потока при исследовании был отклонён площадкой; этот путь в адаптер не включён.
- На этой вкладке разрешены только известные операции чтения Wellfound. Save/delete search, profile/application mutations, неизвестные записи и mutation-документы под разрешённым operation name блокируются. Правила вкладки не устанавливаются на весь browser context и не затрагивают другие площадки или application-вкладку.
- Из текущего поискового черновика Wellfound убираются унаследованные role/city/additional filters, чтобы автоматически полученные Full-Stack Engineer, Buenos Aires, старые keywords, зарплатные и другие дополнительные ограничения не выдавались за GUI-запрос.
- Проверяется выбранный единственный полный keyword в UI и соответствующая конфигурация фактического запроса/ответа. Несовпадение, неизвестный непустой ограничивающий фильтр, ошибки GraphQL или отсутствие подтверждённого ответа не считаются успехом. Допускается собственный native cache только для той же конфигурации при совпадающем текущем UI keyword.
- Карточки извлекаются из `data.talent.jobSearchResults.startups.edges[].node.highlightedJobListings`, а не regex по всем ссылкам/рекомендациям HTML. Компания, title, ID/slug, описание, `liveStartAt`, remote config и provider-applied flag относятся к этому listing.
- Провайдерский `currentUserApplied=true` исключает повторную обработку. Подтверждённая/неопределённая отправка в локальной истории защищает тот же numeric Wellfound ID даже после изменения slug. Пользовательская история не очищается.
- Если нативный поиск недоступен без входа/после изменения сайта, остаётся прежний строгий public fallback только для действительно применившейся точной роли. Переход `/remote` не считается успешным поиском и не даёт общей выдачи под видом целевого запроса.

### Что именно меняется на сайте

Штатные контролы обновляют текущий **поисковый черновик Wellfound**. Это не изменение профиля кандидата, имени/контактов/зарплатных ожиданий в приложении и не создание/удаление именованных saved searches или job alerts. Поисковый draft площадка может запомнить между посещениями; нельзя обещать отсутствие любых изменений её последнего поискового состояния при выполнении нового поиска.

## Ограничения — не скрывать

1. **Company-region scope Wellfound.** На проверенном аккаунте сохранён фильтр компаний `South America`. Он не захардкожен и не выводится из CV: его текущие ID наблюдаются в запросе самой площадки, label читается из её контрола. Адаптер сохраняет и явно показывает этот scope, но **не выдаёт его за GUI-регионы** `North America / Latin America / Europe`. Изменение/корректное сопоставление этой географии остаётся отдельной отложенной задачей. Кроме того, Wellfound сам сообщает, что скрывает вакансии, недоступные из location аккаунта; это не ограничение, подставленное в общий поиск приложения.
2. **Первая страница.** Если `hasNextPage=true`, выводится предупреждение. Нативная пагинация ещё не реализована; больший `pages_per_search` не означает, что все native pages уже проверены. Прежний public Wellfound-адаптер также не обходил страницы.
3. **Live-форма не подтверждена этим прогоном.** Проверялся поиск без вызова application callbacks. Не было свежей прошедшей eligibility вакансии для следующего этапа. Локальные form-regressions не заменяют реальное заполнение.
4. **Изменения сайта.** Селекторы/response contract Wellfound могут измениться; при неподтверждённом состоянии предусмотрен явный отказ, а не молчаливый переход к общей ленте.

## Защита остальных площадок

- Сравнение AST всех не-Wellfound функций `sources.py` с HEAD подтвердило неизменность реализаций (Indeed, Remote OK, Himalayas, We Work Remotely, общий source loop и helpers).
- `apply.py`, `gui.py`, `config.yaml`, `job_metadata.py` в этой задаче не редактировались. LinkedIn использует прежнюю реализацию.
- Тесты проверяют, что native Wellfound-запросы не меняют `CFG`, `SETTINGS`, `PROFILE`, GUI keywords и dispatch остальных площадок. Неуспешный native keyword не запускает другой адаптер и не подменяет его запрос.
- Добавлены проверки literal full phrase, скрытых ограничений, неверной identity/response, provider-applied и старого uncertain slug, strict public fallback, native cache + текущих UI tokens, запрета profile/save/apply mutations, настоящего embedded UI на локальной Chrome-странице.

Полный прогон после реализации: **490 тестов прошли** (включая unit и офлайн браузерные). Команда:

```bash
AUTOAPPLY_BROWSER_TESTS=1 .venv/bin/python -m unittest discover -s tests
```

Это не live-проверка остальных площадок; доказательство их неизменности здесь — дифф/AST и существующие регрессии, а не утверждение об актуальности всех внешних сайтов.
