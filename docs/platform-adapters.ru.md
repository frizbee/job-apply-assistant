# Изоляция платформ и идемпотентность

## Структура

Каждая площадка теперь имеет отдельный файл и класс:

| Файл | Класс / назначение |
| --- | --- |
| `platforms/linkedin.py` | `LinkedInAdapter`: поиск, вход, Easy Apply, draft Continue |
| `platforms/linkedin_resume.py` | Только LinkedIn: upload и выбор CV |
| `platforms/wellfound.py` | `WellfoundAdapter`: native/public search и формы |
| `platforms/indeed.py` | `IndeedAdapter`: пассивный auth wait, поиск, формы |
| `platforms/remoteok.py` | `RemoteOKAdapter` |
| `platforms/himalayas.py` | `HimalayasAdapter` |
| `platforms/weworkremotely.py` | `WeWorkRemotelyAdapter` |
| `platforms/ashby.py` | `AshbyAdapter`: нормализация URL и UUID вакансии |
| `platforms/greenhouse.py` | `GreenhouseAdapter`: job ID, legacy/embed/new URL |
| `platforms/lever.py` | `LeverAdapter`: URL Apply и UUID вакансии |

Общие механизмы не дублируются по площадкам:

- `form_engine.py` — заполнение и повторная проверка значений/выборов;
- `ats_engine.py` — проверенный документ, native form targets, cooldown и dispatch;
- `application_identity.py` — реестр попыток по конечной ATS-вакансии;
- `apply.py` — runtime, профиль/ответы, история, квоты, pending-before-click и
  совместимые публичные функции;
- `sources.py` — общий цикл источников и совместимые entry points.

Размер `apply.py`: **2586 → 1512 строк**, `sources.py`: **618 → 255**.
Состояние и зависимости явно передаются адаптерам; не создаются отдельные копии
настроек, профиля или защиты отправки. Старые GUI/тестовые вызовы сохраняются.
Механический перенос 27 функций проверен сравнением нормализованных AST:
изменений бизнес-логики переносимых потоков не найдено. Регрессии сохраняют
отпечатки основных потоков и запрещают импорт бизнес-логики соседней площадки.

## Причина последовательного CV-timeout

Сбой воспроизведён: первая LawnStarter проходит, вторая/третья и INDI падают
на проверке выбора CV. LinkedIn меняет разметку в пределах браузерной сессии:

1. сначала `div[role=radio][aria-checked]` с вложенным native input;
2. затем только `input[type=radio][aria-label]`, уже checked, без ARIA-обёртки.

Старый код требовал ARIA-атрибут у обоих вариантов и пытался кликнуть уже
выбранный native input, что давало TimeoutError. Теперь native checked обязателен,
а ARIA проверяется на согласованность только если присутствует. Имя/выбор не
признаются только по наличию старой карточки: требуется текущая подтверждённая
загрузка и SHA-256 локального CV. Противоречивые имена/состояния блокируют форму.
Технические исключения upload отмечаются и в `errors`, а не только в manual queue.

## Идемпотентность

Ключ строится только из распознанного HTTPS URL доверенного ATS:
provider + организация + реальный ID вакансии; для Greenhouse/Lever разделены
US/EU tenants. Tracking-параметры и `/application`/`/apply` ключ не меняют.
Названия должностей не используются как новая ATS-идентичность.

- Один ATS job, пришедший с разными LinkedIn/source IDs, обрабатывается один раз.
- Повтор не открывает внешнюю форму, не ждёт cooldown и не расходует её квоту.
- Повтор того же вызова получает сохранённый результат, не новую отправку.
- Квотный пропуск не помечает форму как уже обработанную.
- `application_key`/`application_url` попадают в обычную запись истории, включая
  `submission_pending` **до** клика. Alias ID хранится для дублей.
- Старые ATS URL читаются из истории и manual CSV без массовой миграции/очистки.
- Ручной выбор одной старой queued-копии возможен, но не обходит другую
  pending/uncertain/sent/rejected попытку того же ATS job.
- Смена job ID при redirect или SPA-навигации на том же ATS блокирует заполнение.
- Очередь группирует известные алиасы read-only; новые дубли имеют статус
  `external_duplicate` и отдельный счётчик `duplicates_skipped`.

Ограничения: неизвестная структура URL не получает выдуманный ключ. Реестр
не является распределённым transaction coordinator; нельзя запускать несколько
процессов на одном data-каталоге. Неопределённый сетевой результат не считается
успехом и не повторяется автоматически. Защита по company/title также сохранена.

## Реальные проверки без отправки

В одном persistent браузере последовательно проверены:

- LawnStarter `4470899321`, `4470870587`, `4470870588`: CV загружен и выбран во
  всех трёх формах; TimeoutError исчез. После CV остановка только на собственных
  screening/narrative-вопросах работодателя, ответы не выдумывались.
- INDI `4482123483` после них: **preview / dry_run**, неотвеченных полей нет.
- Финальных Submit calls: **0**. Рабочие история, настройки, CSV и лог не изменены.

Приватные before/after отчёты:

- `data/browser-diagnostics/platform-smoke-20261023T123143853863Z/report.json`;
- `data/browser-diagnostics/platform-smoke-20261023T125039649266Z/report.json`.

В той же after-папке `legacy-identity-report.json`: три tracking-варианта реальной
Kraken-ссылки сопоставлены текущей истории. Все вернули `external_duplicate`,
навигаций **0**, расхода внешней квоты **0**. Это read-only проверка дедупликации,
не новая живая заявка Ashby.

## Тесты и запуск

`AUTOAPPLY_BROWSER_TESTS=1 .venv/bin/python -m unittest discover -s tests`
— **592 теста успешно**. Есть регрессии на последовательную смену DOM CV,
идемпотентный повтор, durable pending с ATS key до клика, legacy evidence,
алиасы очереди, защищённую историю, job-changing redirects и межплатформенную изоляцию.
Реальная доставка заявки и live-работа остальных площадок этим не подтверждены.

Повторяемый ограниченный smoke test:
`.venv/bin/python tools/linkedin_platform_smoke.py --job-id ID --job-id ID2`
— максимум четыре ID, всегда Test mode, отдельные файлы диагностики. Запускать
только когда основной прогон/ручной разбор остановлен. Заполнение и upload могут
передавать данные сайту, хотя Submit отключён.

Пользователю: перезапустить GUI. Настройки, выбранные источники, зарплата,
регионы, пресеты и история не очищались. Для live сначала нужна одна отдельно
разрешённая контролируемая отправка; массовая live-доставка не тестировалась.
