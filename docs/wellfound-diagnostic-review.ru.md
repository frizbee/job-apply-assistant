# Wellfound: диагностический прогон и fix-list

**Последующее обновление:** реализован изолированный нативный keyword-поиск Wellfound по полным GUI-должностям; итоговая live-проверка — 9 подтверждённых запросов из 9, две найденные, но старые вакансии. [Реализация, ограничения и проверка остальных адаптеров](wellfound-native-search.ru.md). Разделы ниже сохраняют историю предыдущих этапов, где native-поиск ещё не был реализован.

## Выполнение выбранных исправлений (после диагностического прогона)

Порядок пользователя: **исключения должностей → безопасная форма/live-проверка → счётчики → поиск последним**. Положительный title matching (пункт 3 пользовательского списка), регионы и remote/hybrid-политику не меняли.

### 2. Пользовательские исключения должностей — выполнено

- В GUI добавлено **Excluded words / phrases in job titles**, настройка `excluded_title_words`, по одному слову/фразе на строку.
- Изначально пусто; `Marketing` не подставлялся за пользователя. Literal case-insensitive matching с границами слов, без regex/скрытого blacklist. Проверяется только title, не описание.
- Поле сохраняется/загружается/очищается, валидируется до публикации настроек. Решение `title_keyword_excluded` содержит `title_diagnostic` с введённым term и title; старые решения сохраняются. Изменение списка меняет ревизию bounded recheck, защиты отправок не ослаблены.
- Regression: Marketing Lead отклоняется только при пользовательском `Marketing`; упоминание marketing в описании Software Engineer не отклоняет его. Старая положительная логика специально не исправлялась: при пустом списке Marketing Lead ещё может пройти, как и было согласовано пропуском пункта 3.

### 4. Привязка Apply и проверка формы — код усилен; live-заполнение заблокировано входом

- Apply выбирается в минимальном блоке единственного соответствующего `h1` текущего job URL; другой job-link в блоке, несколько кандидатов или конфликт aria-label дают manual. Больше нет глобального выбора первой Apply-кнопки из рекомендаций.
- Native submit-capable opener по-прежнему запрещён. Проверяются единственная видимая форма/модальное окно и единственное распознанное финальное действие. Существующая верификация ответов и test-mode guard сохранены.
- Локальная Chrome-фикстура: кнопка рекомендации стоит первой, но не нажимается; правильная форма получает Ruby experience=14; submit-счётчик остаётся 0. Отдельно проверены submit-capable opener, несколько форм и несколько финальных кнопок — все без отправки/preview.
- В реальном сохранённом профиле Chrome повторно открыт Wellfound, дано до 3 минут на ручной login. Вход не завершён; результат `login_required`, финальный URL `/login`. Форм открыто/изменено 0, previews 0, отправок 0. Успешный live-form критерий остаётся **невыполненным**. Не нужно выдавать офлайн-фикстуру за реального работодателя.
- Diagnostics: `data/browser-diagnostics/selected-fixes-20261022T172431Z/live-report.json`. Основные файлы истории/CSV/settings/run.log/last_run не менялись.

### 5. Счётчики — выполнено

- Новый `run_metrics.py`: наборы ID на каждую стадию, сброс перед запуском, контекст текущей application; повторное заполнение шагов не удваивает job-count.
- Итог: `seen`, `history_skipped`, `evaluated`, `rejected`, `manual`, `errors`, `forms_opened`, `forms_changed`, `previews`, `confirmed`, `searches_verified`, `searches_failed`, `submit_attempts`.
- `seen` — уникальные кандидаты, дошедшие до учитываемого workflow/явного history-skip, не обещание посчитать все ссылки, отфильтрованные внутри каждого внешнего feed-адаптера. `evaluated` — допущенные историей к оценке. `forms_opened` отмечается при входе в реальное заполнение; `forms_changed` — наблюдаемое изменение значений controls, **не** гарантия полного ответа на все вопросы. Только preview отражает достижение финальной guarded-стадии в test mode.
- При test mode previews не выдаются за реальные submit attempts. Existing quotas/reservations/uncertain-history не заменялись метриками и не ослаблялись. Итог `Tested` удалён; GUI видит те же счётчики через обычный журнал.
- Integration regression: два просмотренных/оценённых отказа дают `seen: 2 | evaluated: 2 | rejected: 2` и `previews: 0`, а не `Tested: 0`.

### 1. Поиск последним — ошибочный fallback исправлен, поддержка произвольных полных названий ограничена площадкой

- Перед обработкой карточек проверяются фактический requested URL и точный видимый role-selection в контроле поиска; bounded ожидание гидратации.
- Редирект `/remote`, другой host/path, отсутствующий/другой выбранный role не дают ни одного кандидата этой ветки; явное сообщение содержит requested/actual URL. Увеличивается `searches_failed`, общий feed не обрабатывается под видом Ruby/Rails-запроса.
- Live-проверка текущих первых трёх пользовательских запросов: все три отвергнуты площадкой и ушли на `/remote`; приложение корректно обработало **0 вакансий общей выдачи**, зарегистрировало **3 failed searches**. Это не заявляется успешным поиском этих полных названий.
- Отдельные read-only проверки таксономии (не сохранены в GUI): точные `Ruby on Rails Developer` и `Backend Engineer` сохраняют свой URL и точный role-selection, новая проверка возвращает true. `Senior Ruby on Rails Developer` / `Senior Backend Engineer` в исследованном публичном контроле не имеют точного варианта; выбирать broad default вместо них запрещено.
- Автоматическое снятие seniority, приведение к предполагаемому taxonomy-id или смена GUI-должностей **не реализованы намеренно**. Для произвольного free-text поиска нужно отдельно исследовать авторизованный поиск площадки либо согласовать с пользователем явное сопоставление его должностей поддерживаемым search-ролям. Сейчас unsupported-role ветка честно прекращается, вместо массового нерелевантного обхода.
- Diagnostics: `data/browser-diagnostics/selected-fixes-20261022T172431Z/search-verification-report.json`. SHA-256 шести основных data-файлов совпали до/после.

**Итоговая проверка выбранных исправлений: 478 тестов прошли**, включая реальные embedded GUI JavaScript tests и локальные Chrome-формы/редиректы. Команда: `AUTOAPPLY_BROWSER_TESTS=1 .venv/bin/python -m unittest discover -s tests` (79 секунд). Реальных отправок не было. Контакты, зарплата, CV, GUI-регионы и списки пользователя не менялись.

Дальнейший текст — исходная диагностика до перечисленных исправлений; статусы «не исправлено» ниже следует читать с учётом этого раздела.

Дата: 2026-10-22. **Исправления кода в этом задании не выполнялись.** Цель — ограниченная проверка реального браузера и список подтверждённых дефектов после предыдущего пользовательского запуска.

## Результат и границы прогона

- Реально открыты **3 поисковых URL** по первым трём должностям из сохранённого GUI-списка и **5 страниц вакансий** из предыдущего запуска.
- Принудительно включён `DRY_RUN=True`, независимо от сохранённого режима. LLM-запросы не выполнялись.
- Одна прошедшая текущие фильтры вакансия доведена до application-flow приложения. **Блокер: вход в Wellfound**, переход на `https://wellfound.com/login`. Учётные данные не вводились; CAPTCHA не обходилась.
- **Открытых форм — 0, заполненных реальных форм — 0, previews — 0, отправок — 0.** Не следует считать это успешным end-to-end заполнением.
- Перед application-flow дополнительно заблокированы все HTTP-записи, кроме GET/HEAD/OPTIONS, и нативный submit. Заблокирован один POST на telemetry endpoint `https://rddrstck.wellfound.com/v1/page`, не endpoint входа или отклика. Этот диагностический guard намеренно не обходился.
- История использовалась в изолированной копии. SHA-256 шести основных файлов (`applied.json`, `applications.csv`, `manual_apply.csv`, `user_settings.json`, `run.log`, `last_run.txt`) до/после совпадают. Основные **53 записи сохранены без изменений**; поисковые регионы, зарплата, контакты и CV не менялись. Обычный широкий `run_bot()` не запускался: это целевой ограниченный live-прогон, а не повторный обход всей выдачи.
- Независимая проверка: **463 теста прошли** командой `AUTOAPPLY_BROWSER_TESTS=1 .venv/bin/python -m unittest discover -s tests` (76 секунд). Локальные браузерные тесты не заменяют live-форму.

Сохранённые GUI-регионы: `North America`, `Latin America`, `Europe`. Целевые и исключаемые технологии сейчас **пусты**; приложение не добавляло их за пользователя. Выбрана площадка Wellfound.

## Что воспроизведено в поиске

| Переданная должность | Запрошенный путь | Фактический путь |
|---|---|---|
| Senior Ruby on Rails Developer | `/role/r/senior-ruby-on-rails-developer` | `/remote` |
| Senior Ruby on Rails Engineer | `/role/r/senior-ruby-on-rails-engineer` | `/remote` |
| Senior Ruby Developer | `/role/r/senior-ruby-developer` | `/remote` |

Во всех трёх случаях получена финальная страница HTTP 200 с title `Remote Tech & Startup Jobs | Wellfound`, заголовком `Remote Tech & Startup Jobs`, выбранным **any roles**, количеством **12058 results total**, `Page 1 of 211`.

Все три набора содержат **одинаковые 53 ID**, в точности совпадающие с 53 ID предыдущего пользовательского прогона. Все 53 ID также найдены в видимых DOM-ссылках. Поэтому прежняя гипотеза «эти 53 нерелевантные вакансии взялись только из скрытых рекомендаций» **не подтверждается**: доказанная причина — переход на общую remote-выдачу без заданной роли. Риск широкого сбора ссылок из всего HTML остаётся отдельной проблемой реализации.

## Подтверждённый fix-list

### WF-01 — P0: не принимать общий fallback за результат поиска по должности

**Статус:** воспроизведено в реальном браузере, не исправлено.

`sources.py:232–237` строит slug из полной должности GUI. Проверенные URL переводят на `/remote`, но адаптер продолжает обработку как будто роль применена. Отсюда повторные 53 вакансии любых направлений вместо Rails/backend-поиска.

**Исправление:** исследовать реальные поисковые controls/контракт Wellfound и передавать пользовательскую должность поддерживаемым способом. Проверять не только HTTP 200, но и фактически применённые role-фильтры после редиректов/гидратации. Если фильтр не применился — явная диагностика и остановка этой поисковой ветки, без обработки общей выдачи как целевой. Не подменять введённые роли собственным списком профессий или guessed taxonomy.

**Критерий приёмки:** разные выбранные роли действительно отражены в состоянии поиска; fallback `/remote` с `any roles` обнаруживается и не запускает массовую обработку.

### WF-02 — P1: реально применять регионы GUI в Wellfound

**Статус:** подтверждено кодом и отправленными live-URL, не исправлено.

Функция `wellfound()` использует только keywords; значения `North America / Latin America / Europe` не передаются и не проверяются. На фактической странице выбран только Remote. Это не означает, что сохранение GUI-списка сломано: проблема в адаптере площадки.

**Исправление:** связать поиск с точным пользовательским списком через поддерживаемые controls/идентификаторы площадки. Проверять применённые значения; если площадка не поддерживает введённый регион, объяснить это, а не молча заменить страной кандидата, Worldwide или другим регионом. Разделять географию поиска, локацию офиса и ограничения найма.

**Критерий приёмки:** каждый GUI-регион либо подтверждён в действующем фильтре, либо даёт явное сообщение о неподдерживаемом значении; никаких скрытых подстановок.

### WF-03 — P0: конфликт structured remote и обязательной работы из офиса

**Статус:** подтверждено на реальной странице и её сохранённом DOM, не исправлено.

Swoop Backend (`1583809`): `page_metadata()` вернул `workplace=remote`, и отдельная `eligibility_reason(..., remote_only=True)` вернула `None`. При этом detail-карточка содержит:

> Remote Work Policy: In office - WFH flexibility

А в сопоставленном описании:

> This is a hybrid position that requires someone based in Minneapolis/St. Paul OR Washington, DC who can work in-office 3+ days per week

В этой вакансии полный отбор останавливается другим настроенным правилом (`security clearance`), но это **не исправляет дефект remote-only gate**. При другом описании такой metadata-конфликт может остаться незамеченным.

**Исправление:** собирать workplace-policy из проверенного блока текущей вакансии вместе с JSON-LD и явными обязательными условиями описания. При обязательном офисе/hybrid не принимать более оптимистичную generic remote-метку; противоречие без надёжного разрешения — manual с обоими фрагментами. Нельзя считать страницу `/remote` доказательством fully remote. Это разбор условий работы, не новый список исключаемых технологий.

**Критерий приёмки:** этот snapshot не проходит remote-only; тесты покрывают office+WFH, hybrid и конфликт JSON-LD/DOM без захвата данных соседних вакансий.

### WF-04 — P1: точность title matching после удаления скрытой Rails-политики

**Статус:** воспроизведено локальным вызовом текущей реальной функции с сохранёнными GUI-настройками, не исправлено.

`apply_cv_profile()` объединяет слова всех выбранных должностей в один OR и role-токены в другой OR (`apply.py:2097–2101`). Поэтому `job_ok('Product Marketing Lead', 'Cooklist', '')` возвращает `None`: слово `lead` удовлетворяет обоим условиям. Целевые технологии пусты, как и задано пользователем, и не должны быть тайно заполнены Rails ради обхода этой ошибки.

**Исправление:** сохранять связь meaningful-токенов внутри каждой выбранной роли и учитывать контекст роли. `Lead`/`Senior`/`Engineer` не должны сами доказывать соответствие полному пользовательскому направлению. Не возвращать встроенные blacklist профессий/языков; при неоднозначности — manual с объяснением. Семантика технологий остаётся только пользовательской.

**Критерий приёмки:** для текущего набора software/backend/Ruby-должностей Marketing Lead не проходит только из-за Lead; реальные варианты выбранных software/backend-направлений продолжают оцениваться по пользовательским правилам.

### WF-05 — P1: счётчики стадий вместо неоднозначного Tested

**Статус:** подтверждено реализацией и прежним журналом, не исправлено.

`sources.run()` увеличивает `count`/`done` только для `applied`, `applied_external`, `dry_run` (`sources.py:415–417`); финальное сообщение называет count `Tested` (`apply.py:2264`). Это не число просмотренных вакансий. Отсюда 53 проверенных записи и `Tested: 0` одновременно. Лимит `per_source` также ограничивает успешные результаты/попытки, а не число просмотренных карточек.

**Исправление:** отдельные счётчики collected/unique/history-skipped/evaluated/rejected/manual/forms-opened/forms-filled/previews/submit-attempts и причины остановки. При необходимости отдельный явно именованный лимит на просмотр, не переосмысливать без согласования существующий лимит отправок.

**Критерий приёмки:** просмотр N вакансий с нулём форм выводится именно как N просмотренных, 0 форм, 0 previews; отказ на входе не считается заполнением.

### WF-06 — P2: область сбора карточек и пагинация

**Статус:** широкий сбор/отсутствие пагинации подтверждены кодом; лишние ID именно из скрытых рекомендаций в этой live-выборке не обнаружены.

Адаптер ищет `/jobs/...` regex по всему `page.content()`, не по подтверждённому result-контейнеру. Целевая страница показывает `Page 1 of 211`, а `wellfound()` не обходит страницы согласно `pages_per_search`; циклы только по keywords и собранным ID.

**Исправление:** собирать карточки из проверенного контейнера действующего поиска, сохранять provenance query/region/page, исключать прочие блоки и служебный JSON; добавить ограниченную поддерживаемую пагинацию и проверку повторяющихся страниц. Дедупликация — после проверки принадлежности выдаче.

**Критерий приёмки:** fixtures с рекомендациями/скрытыми ссылками и двумя страницами; сбор только из нужной выдачи, соблюдение пользовательского лимита страниц, отсутствие циклов на неизменившейся странице.

## Блокер и следующие проверки

- **Вход в Wellfound:** нужен пользовательский вход в браузерный профиль приложения. Это ограничение текущей live-проверки, не доказательство дефекта заполнителя. Желательное UX-улучшение — проверка авторизации перед долгим обходом, с явным запросом действия пользователя; не требовать логин для исключительно публичной read-only диагностики.
- **Live-форма:** после входа и исправления поисковых/remote gates повторить одну подтверждённо подходящую вакансию с test mode. Критерий — наблюдаемое изменение доступных полей, проверка unanswered и ноль submit. Сейчас этот критерий **не выполнен**.
- **Apply-opener:** на проверенных job-pages найдено 8–11 кнопок `Apply` по глобальному селектору; `wellfound_apply()` берёт `.first`. Неверный клик не воспроизведён, потому что приложение раньше остановилось на login. Нужно отдельно проверить привязку opener к текущей вакансии после входа; это риск, а не заявленный подтверждённый misclick.
- **Новые GUI-технологии:** сохранённые списки пусты, поэтому произвольные реальные пользовательские исключения live не проверялись. Их load/save/clear и фильтрация покрыты локальными тестами. Вводить технологии за пользователя в диагностике нельзя.
- **Остальные площадки:** в этом live-прогоне не проверялись. Нельзя переносить выводы о Wellfound на LinkedIn/Indeed/feeds.
