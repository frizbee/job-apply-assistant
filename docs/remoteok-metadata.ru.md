# Remote OK: устранение ложного workplace_unknown

## Дополнение: полное описание и точная ссылка Apply

`RemoteOKAdapter.prepare_job()` загружает detail-страницу **после проверки
истории**, но до description-dependent фильтров и поиска инструкций. Известные
старые/onsite/hybrid записи отсеиваются без лишней загрузки. Общий цикл вызывает
изолированный detail-loader; для остальных источников поведение не меняется.

В `platforms/remoteok.py` находятся общий валидатор строки вакансии и JS разбора
description/Apply. Текст берётся из соответствующей соседней `tr.expand` с тем
же ID, из `.description > .html` / `.markdown` либо из проверенного JobPosting.
Проверяются URL, ID, локальный заголовок и компания. Рекомендации, общий текст
страницы и данные другой вакансии не используются. Инструкции, добавленные
Remote OK только в API, сохраняются вместе с полным текстом; точные включённые
подстроки не дублируются. AI не вызывается.

Пустой/неоднозначный или явно обрезанный текст не считается полным. Многоточие
распознаётся также в искажённой кодировке и перед рекламным суффиксом
`Apply now and work remotely at…`; attention-check boilerplate не маскирует
обрыв основного текста. Такая запись получает `metadata_manual` с причиной
`description_unknown`, без открытия формы. Это эвристика явного обрыва,
не гарантия полноты произвольного текста работодателя.

Apply выбирается только среди видимых `a.action-apply[data-job-id=ID]` в
проверенном detail-блоке. Разрешён текущий native HTTPS `/l/ID`, без подмены
другим ID, внешним origin или неоднозначными адресами. Две кнопки с одним и тем
же назначением допустимы. Перед выбором сверяется неизменность описания и ссылки.
Поиск всех Apply-кнопок на странице больше не используется. Конечный ATS
по-прежнему проходит общие whitelist, identity, history, quota и Submit-защиты.

Живая read-only проверка:
`data/browser-diagnostics/remoteok-detail-readonly-20261024T231816922985Z/report.json`.

- DuckDuckGo: полный доступный текст получен, инструкция из API сохранена,
  точная ссылка — `/l/1137551`.
- Rain: remote/date подтверждены, но сама страница Remote OK и её JobPosting
  дают обрезанный основной текст. Теперь это `description_unknown`, а не
  выдуманное полное описание. Автоматический Apply не разрешён.
- HTTP 200 у обеих страниц, кликов Apply/Submit 0; рабочие history/CSV/settings/
  run.log не изменились. Это не проверка конечных форм или реальной доставки.

**669 тестов прошли**, включая новые detail-first фильтры, сохранение API-
инструкций, обрыв текста, source-blocking, историю, изменение описания и
точную маршрутизацию Apply. Перед повторным пользовательским тестом нужно
перезапустить GUI. Существующие ручные заявки не разблокируются автоматически.

## Предыдущее исправление workplace_unknown

У вакансий Senior Backend Engineer от DuckDuckGo (`1137551`) и Rain (`1137544`)
API не содержит отдельных workplaceType/remote, а location пуст. Однако на
страницах конкретных вакансий JSON-LD JobPosting явно содержит
`jobLocationType: TELECOMMUTE` и дату публикации.

Общий парсер не принимал этот JobPosting без URL/@id: для безопасности он
сверял title со всем `h1` страницы. У Remote OK общий заголовок содержит префикс
`Remote`, а локальный `h2[itemprop=title]` — нет. Это давало ложное отсутствие
метаданных, хотя необходимые данные присутствовали.

## Исправление

- Для Remote OK определяется numeric job ID из URL страницы.
- Используется только видимая `tr.job#job-ID` с совпадающими `data-id` и
  `data-href`; ссылка должна принадлежать текущему origin и тому же detail URL.
- JSON-LD читается только внутри этой строки, заголовок сверяется с её
  локальным `[itemprop=title]`/`h2`. Другие карточки и глобальные рекомендации
  не используются как доказательство текущей вакансии.
- Явные location/workplace labels также берутся только из выбранной строки.
  Сама принадлежность Remote OK не делает вакансию удалённой автоматически.
- Общие запреты onsite/hybrid, проверка давности, CV, вопросы и история
  отправок не ослаблены. Несколько анонимных JobPosting не угадываются.

Версия парсера в механизме перепроверки обновлена. Старые `metadata_manual`
могут проверяться снова в рамках уже включённого `recheck_enabled`, существующих
лимитов и защиты истории. Настройки, лимиты, старые решения и защищённые
отправки не очищались и не разблокировались.
