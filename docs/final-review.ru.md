# Дополнительные замечания финальной проверки

Дата: 2026-10-21. Продолжение `code-review.ru.md`: первоначальные восемь исправлений прошли свои тесты, но финальная проверка выявила ещё шесть сценариев. Пункты № 1–3 исправлены; № 4–6 открыты. Следующий — № 4.

До исправления критичных пунктов № 1–4 нельзя полагаться на тестовый режим на реальных площадках. Проверки ниже воспроизводились на локальных HTML-фикстурах с заблокированной сетью и предотвращённой реальной отправкой.

## 1. Неизвестная финальная кнопка обходит тестовый режим — P1

- [x] Исправлено и проверено
- Где: `apply.py`, `apply_to_job()` и повторное нажатие кнопки после ошибки шага.
- Воспроизведение: кнопка `Отправить заявку` в footer считается переходом Next. При `DRY_RUN=True` произошли два события submit без защитной записи в истории.
- Последствия: реальная подача в тестовом режиме и возможность повторной подачи после сбоя.
- Решение: явная классификация известных действий Next/Review/Submit. Неизвестные или противоречивые подписи направлять на ручную проверку без клика. Повтор шага заново проверяет действие кнопки; финальная отправка всегда идёт через общий защитный механизм. Аналогичную классификацию применять к Indeed.
- Проверка: неизвестные подписи в обоих режимах не отправляют форму; известные Submit не нажимаются в тестовом режиме; Next работает; смена Next на Submit перед повтором не обходит защиту.
- Результат: введены точные списки навигационных и финальных подписей. Неизвестные/противоречивые text/ARIA передаются на ручную проверку. Переходы и повтор шага заново проверяют действие и нативный тип кнопки. Общий `submit_application()` дополнительно запрещает отправку при DRY_RUN независимо от проверки вызывающей стороны. Indeed использует ту же классификацию.

## 2. Yes/No-кнопка может отправить форму во время заполнения — P1

- [x] Исправлено и проверено
- Где: `apply.py`, `fill_yesno()` и клики по элементам управления при заполнении.
- Воспроизведение: `<button>Yes</button>` внутри формы по умолчанию является submit-кнопкой. Выбор подтверждённого Yes вызвал submit при `DRY_RUN=True`, без записи попытки в историю.
- Последствия: преждевременная отправка анкеты до проверки остальных вопросов и до общей защиты Submit.
- Решение: при заполнении не нажимать нативные submit/image-кнопки, кнопки без безопасного `type="button"`, их дочерние элементы и обёртки, способные активировать submit. Не менять тип кнопки на безопасный искусственно; сомнительный элемент передавать на ручную проверку.
- Проверка: кнопки без type, с type=submit/image и небезопасные пользовательские radio/option не отправляют форму; обычные Yes/No с type=button продолжают работать.
- Результат: общий `click_form_control()` проверяет нативную семантику элемента, предков, дочерних элементов и связанного label/control. Ограничение submit-типов сохранено в самом локаторе на случай смены type после проверки. Защита применяется к заполнению, открытию форм, навигации, переключению ATS-вкладки и Discard; единственный намеренный финальный клик остаётся в `submit_application()`. Небезопасный элемент не переименовывается и не исправляется в DOM — требуется ручная проверка.

## 3. Два запроса Start обходят признак работающего бота — P1

- [x] Исправлено и проверено
- Где: `gui.py`, `start()` и присвоение `STATE["running"]` внутри worker.
- Воспроизведение: два запроса до выполнения worker оба вернули ok, создали два потока; второй запрос изменил глобальный DRY_RUN с true на false.
- Последствия: изменение настроек активного запуска, обход лимитов и риск одновременных попыток/конфликтов истории.
- Решение: атомарно резервировать запуск под lock до изменения общих настроек. Снимать резервирование при ошибке подготовки или старта потока. Не полагаться только на отключение кнопки в браузере.
- Проверка: конкурентные запросы создают ровно один worker; отклонённый запрос не меняет режим/настройки; ошибка запуска позволяет повторить Start.
- Результат: `ACTIVITY_LOCK` резервируется неблокирующим захватом до проверки/изменения общих настроек; `running=True` публикуется до создания потока. Резервирование передаётся worker и освобождается только в его `finally` после завершения, ошибки или остановки.
- Повторный Start возвращает `already_running`/`busy` без изменения памяти, файла настроек, режима DRY_RUN и источников. Не требуется полагаться на отключение кнопки в браузере.
- Загрузка и анализ CV используют ту же блокировку: они не могут заменить активный файл или профиль работающего бота, а Start не может обойти незавершённый анализ. Ключевые настройки запуска (режим, английский, список источников и регионов) проверяются до публикации.
- При ошибке подготовки, конструктора или запуска потока резервирование снимается, общие настройки в памяти восстанавливаются, интерфейс получает `startup_failed` с диагностикой. Файл настроек при ошибке запуска потока может уже содержать выбранные пользователем валидные предпочтения; это не транзакция файловой системы и не блокировка нескольких процессов приложения.
- Stop очищается при принятии нового запуска, а GUI-worker вызывает `run_bot(reset_stop=False)`. Поэтому Stop, пришедший во время ожидания worker, не стирается; при такой отмене браузер не запускается. Терминальный вызов сохраняет прежнее поведение сброса Stop по умолчанию.
- Добавлен `tests/test_start_concurrency.py`: 19 unit-тестов, включая реальные конкурентные потоки запросов, отложенный и уже работающий worker, немедленное завершение, отказ без перезаписи файла, ошибки запуска, остановку и взаимоисключение с CV-операциями. Бот, браузер и запросы ИИ в этих тестах подменены.
- Полный локальный прогон на Python 3.12/Node.js 22: **213 тестов прошли — 171 unit и 42 браузерных**. Реальные отклики не отправлялись.

## 4. Подтверждённый radio-ответ может не примениться — P1

- [ ] Исправлено и проверено
- Где: `apply.py`, `fill_radios()`.
- Воспроизведение: заранее выбран Yes, подтверждён No. Клик по текстовой div-обёртке не меняет radio, но проверяется наличие любого выбранного варианта; остаётся Yes, список неизвестных вопросов пуст.
- Последствия: отправка противоположного ответа, в том числе на юридически значимый вопрос.
- Решение: проверять состояние именно целевого radio, а не группы в целом; для role=radio проверять aria-checked. Если выбор не подтверждён, блокировать анкету.
- Проверка: заранее выбранный противоположный вариант, неподключённая label/div-обёртка и custom radio с неработающим кликом не считаются корректным ответом.

## 5. Расчёт зарплаты угадывает курс и период — P2

- [ ] Исправлено и проверено
- Где: `apply.py`, `salary_answer()`.
- Воспроизведение: при зарплате 60000 USD и недоступном FX вопрос в GBP получает 60000 GBP. Вопрос `Annual salary rate in USD` получает 29 вместо 60000, потому что слово rate считается часовым периодом.
- Последствия: неверные зарплатные ожидания в отправленных анкетах.
- Решение: не конвертировать без подтверждённого курса; неизвестную валюту/период передавать на ручную проверку. Явные annual/monthly/hourly имеют приоритет над неоднозначными словами. Нулевое/отсутствующее ожидание не заменять выдуманным минимумом.
- Проверка: недоступный FX, неизвестная валюта, явный годовой rate, месячные/часовые суммы, пустая и нулевая зарплата.

## 6. Сохранение Unicode зависит от системной кодировки — P2

- [ ] Исправлено и проверено
- Где: чтение/запись JSON истории и настроек в `apply.py`.
- Воспроизведение: запись Unicode-названия вакансии в окружении с ASCII-кодировкой вызвала UnicodeEncodeError. Аналогичный риск есть на Windows с legacy code page.
- Последствия: невозможность сохранить профиль или попытку подачи; остановка обработки не-ASCII данных.
- Решение: явно использовать UTF-8 для чтения и записи JSON/текстовых файлов с пользовательскими данными. Сохранить атомарную замену истории и поведение fail-closed при ошибке записи.
- Проверка: профили, названия вакансий и пути с кириллицей/CJK в non-UTF-8 окружении сохраняются и читаются без изменения данных.

1. Сначала № 1–2: обходы тестового режима и защиты финальной отправки.
2. Затем № 3–4: конкурентный запуск и проверка точного выбранного ответа.
